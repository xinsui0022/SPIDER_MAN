# 设定档4重进任务消失：检查点 Hook 只读审计

本轮只读检查本机二进制、现有运行时 Hook 快照及 JSON 配置；没有改 DLL、EXE、存档、进程内存或 UI。新增 Python 工具与报告只写入调查目录。

## 结论与范围

**当前没有找到一个可据此安全关闭的“禁止自动检查点” Hook，也没有找到控制它的配置项。** 现有“任务阶段推进，但 CampaignSave 检查点和 LastPosition 保持最初值”的现象值得继续比较，不过不能仅凭这几个字段就判定 MOD 刻意禁用保存。

检查使用 game v4.630.0.0、core smt.dll 原件，以及 PID 37700 的旧 `.text` 修改快照 `已加载Hook映射.json`。旧快照并非 PID 27180 的本次全部运行时状态；本轮没有捕捉新进程的虚表改写或间接状态写入，因此不能排除这些影响。

## 已确认的保存目录 Hook

- 原版入口：game RVA `0x190A8A0`。
- 旧加载快照目标：core RVA `0x1ADB0`。
- 原版函数负责构造 / 检查保存根目录；日志字符串包括 `Failed to create root directory for savegames %ls` / `LocalSave`。
- core 实现先通过 `core + 0xBE968` 调用原入口，保留返回值，再把输出目录改成 `SMT/Save/`，最后返回原入口状态。
- 这段实现没有直接取消保存请求，没有判断主机 / 客机后跳过保存，也没有直接清空 CampaignSave 的 CurrentCheckpoint 或 LastPosition。

## 与检查点有关的原版入口

从原版 RTTI 的 TypeDescriptor → CompleteObjectLocator → 虚表解析得到：

| 类 | 虚表 RVA | 方法数 | 与旧 Hook 入口重合 |
|---|---|---:|---:|
| AutoCheckpoint | 0x38AD3A8 | 10 | 0 |
| AutoCheckpointAction | 0x38B7390 | 11 | 0 |
| CheckpointAction | 0x4F6B150 | 15 | 0 |
| CheckpointQueryAction | 0x4F6B270 | 11 | 0 |

CheckpointManager 初始化 / 注册字符串位于函数 `game 0x1F7D040` 内，旧快照亦没有相同入口的 Hook。这里的“0”只表示入口没有出现在旧 `.text` Hook 清单，不能证明调用链的每个子函数和数据字段均未受影响。

曾怀疑的 game `0xC21C50`、`0xC24D40`、`0xC26760`、`0xC271C0`、`0xC2A260`、`0xC2B8E0` 一组 core 实现明确取用字符串 `RandomCrimeSystem2`，配合原版 Prefab / actor 处理，不能把它们仅凭地址接近就标成检查点保存 Hook。

## 仍值得核对的任务恢复分支

旧快照在 game `0xC027F2` 将 7 字节替换为 NOP。原版这里是 `cmp eax,0x5ED9BFD9` 与 `jne 0xC02824`，所在函数 `0xC027B0` 在特定模式分支内解析当前目标，随后可调用 `0xC00220` 单任务启动函数。

因此可确定 MOD 改宽了某个任务相关分支的条件。但目标值 `0x5ED9BFD9` 的具体语义、该分支在本次重进是否执行，以及它与保存检查点是否有关尚未核实。**这不是已定位的修复点，不能恢复 / 禁用这段修改后就宣称解决。** 需要在冻结存档副本的原版与 MOD 同阶段重载对照中核验任务状态、场景和后续事件。

## 配置项与误判风险

当前 `SMT/Preferences.json` 只有 RPC、控制台、ImGui 等偏好；`SMT/Multiplayer.json` 涉及外观、随机犯罪、难度、移动和可见性，没有自动保存、检查点或故事模式恢复选项。

其中 `EnemyHealthMultiplier=0.0` **不等于敌人零血量**：core `0x631E0` 先取原数值，取配置值后执行 `(1 + 9 * 配置值) * 原数值`；常量 1 位于 `core 0x7B70C`，9 位于 `core 0x8420C`，对应配置读取为 `core 0x633A0` → `EnemyHealthMultiplier` 字符串 `0x83E58`。所以这里 0 对应原倍率，不能把配置改成 1 作为修复。EnemySpawnMultiplier 的独立应用语义本轮未展开验证。

## 推荐的下一项有效验证

冻结当前主档和同槽自动档，确认序章前九目标已完成、SECOND_STOP_FINISH 正在进行这组状态是否已写入磁盘。用相同快照在无 MOD 环境加载，记录是否返回正确位置、该目标是否自然恢复并完成。若原版同副本也缺标记，应检查 checkpoint 与脚本状态的组合；若原版恢复而 MOD 不恢复，再围绕实际执行的恢复分支定位。不要继续用最初教程档覆盖当前进度，也不要仅手改检查点编号或强制目标完成。
