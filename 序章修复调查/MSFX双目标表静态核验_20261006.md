# MSFX 两份目标表的有限静态核验

本次仅读取原版 EXE、MOD DLL 与已有审计记录；未操作游戏、UI、进程内存或存档。游戏 SHA256 为 `e297d4d94f1ffe4febf289745e79e7b6fa233a788e7a00f480fc77c55db81ad1`，核心 DLL SHA256 为 `b7ab575100f2346af25180d74bf9641e24ce09bf549ce47446be09c3462606c7`。以下地址为对应文件 RVA。`M` 表示原版任务管理对象起点。

## 已确认

- 原版 `C00FE0` 写入 MSFX 魔数，当前文件版本为 35；先调用原版 `1FABFB0`，再写其余管理状态及四块缓存。原版 `BFC5D0` 读取 MSFX 并调用 `1FA9A20` 恢复前一部分。两份表均由原版保存器设计写出，并不是仅因 MOD 存档才出现。
- 第一份目标行步长 24 B，由 `1FABFB0` 写出：目标 hash 后依次为主状态数组 `M+0x280`、`M+0x4280`、`M+0x8280`、`M+0xC280` 的四个字，以及 `M+0x30484` 的附加字；每个活动任务另有索引步长。原版 `1FA9A20` 对应读取并恢复这些数组。
- 第二份目标行步长 20 B，位于 `C00FE0` 的四块循环。第 0 块状态数组起点为 `M+0x94AB8`、`M+0x98AB8`、`M+0x9CAB8`、`M+0xA0AB8`，第 n 块加 `n*0x38548`。行内容为目标 hash 与上述四个字。原版 `BFC5D0` 分别恢复这四块，未发现把两张磁盘表当作同一缓冲区处理的直接证据。
- 原版 `BFD600` 本身实现主状态到所选第 n 块的复制。例如其 `BFD775` 一带读取主数组 `M+0x280` 等，并写入该块的四个对应数组。因此，两表共有五个字相同，可以由原版状态复制设计自然产生；不能据此认定 MOD 把当前状态错误覆盖到检查点快照。此次没有确定该函数的实际调用时机。
- 原版 `BF8D70` 实现相反方向的状态恢复，读取所选缓存块并恢复主数组；`BF8F59` 一带还根据目标定义的 `+0x72` / `+0x73` 标志调整加载状态。前表加载器 `1FA9A20` 的 `1FA9D5F` 一带也存在相同类型的标志分支。此次未核验这些偏移与字段名的对应关系，故不直接命名为 NoSave / NoSaveMission。
- 旧运行快照 `已加载Hook映射.json`（PID 37700）没有直接修改以上 MSFX 保存器、加载器或两个复制函数。此结论只覆盖该次快照里的已映射直接改码，不能排除其他调用路径、数据修改或条件变化。

## 已映射 MOD 改码的有限范围

- `C027F2` 的 7 B NOP 原本是 `cmp eax,0x5ED9BFD9` 与条件跳转。它放宽一个任务条件，所见函数没有复制两表的目标数组。目标 hash 的含义仍未确认。
- `BF91C0` 被转到核心 `1CC00`，后者只有 `mov al,1; ret`。原版 `BF91C0` 检查任务状态、活动目标状态以及目标定义字段，返回条件结果；它本身不是上述双表复制函数。原版调用点还把返回结果传往另一系统，但此次未追完整语义。它可列为后续有条件地核验的候选，不能据此认定根因或直接回退 Hook。
