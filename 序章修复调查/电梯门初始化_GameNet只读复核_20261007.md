# Fisk 电梯门客机关闭：有界只读 GameNet 复核

## 结论

**已确认 SMT 的 initial/game/load 阶段读自游戏保留的 GameNetManagerBase，并接入实际 GameStateSystem 流程；未确认 Fisk 电梯门或其碰撞状态进入快照。** 不能继续把阶段文案当作“完整世界同步”的证据，也不能只因找不到 door 字符串就断言门同步未实现。

用户现象：主机门已打开后客机才加入；客机敌人也已清空、显示目标与主机一致，但同扇门仍关且有碰撞。它说明现有入场路径未把本次通路恢复到与主机一致。具体可能发生在快照采集、字段应用、脚本事件补放、载入后覆盖或场景实例对应关系，本轮没有逐项证明。

## 已确认代码证据

本轮重新核对两文件 SHA-256 与既有固定值一致。位置均为模块 RVA，不是运行时绝对地址。

- core `0x29B80` 读取 `[core+0xBFC70]` 指向的全局槽，再读取槽中的对象。
- core `0x29C6A` 把签名解析结果写到 `0xBFC70`；签名文本在 core `0x79058`。该签名在当前游戏文件唯一匹配 game `0x1EFF2A6`，其 RIP 位移直接指向 game `0x7C2B1C0`。
- game `0x1EFF270` 构造对象，把虚表 `0x4F63AF0` 写到对象头，再把该对象存入 `0x7C2B1C0`。虚表前的 COL→TypeDescriptor 解析到 `.?AVGameNetManagerBase@@`。
- core `0x49726` 调用 `0x29B80`，随后读对象 `+0x10` 选择连接提示。游戏自身 `0x1EFF330` 从同字段选择 `kConnectingToServer`、`kSyncingInitialState`、`kSyncingClients`、`kCreatingClients`、`kSyncingGameState`、`kCreatingGameState`、`kSyncingLoadState`、`kRequestingGameEntry`、`kConnected`、`kConnectError`，数值依次为 1..10。
- 游戏全局 `0x63C9080` 的静态虚表 `0x4F64320` 通过 RTTI 闭环为 `GameStateSystem`。game `0x1EFFA70` 的分支调用 `0x1F02A00`，传入该对象和回调；返回成功后设置管理器 `+0x10=6`。`0x1F02A00` 保存回调，然后转入 `0x1F02B10`；后者按计数发起条目工作，最后调用完成回调。相邻路径进入 `0x1F04BD0` 后将阶段设为 7。

最后一项只证明实际状态初始化工作与完成回调，不证明条目内容是门，也不把未恢复符号的函数冒充 Get/Sync 初始状态函数。

## 本轮未闭合的关键问题

未恢复出对应本次 Fisk 门的对象 ID、脚本状态字段、门开闭事件、碰撞启停字段；没有两端应用快照前后对象状态；没有这次连接期间收发载荷。因此不能断言“initial state 漏了门”，不能给出已验证的 DLL 字节补丁，不能宣称重置存档能解决网络剧情同步。

## 有据调查/修复方向

先检查游戏 `GameStateSystem` 注册/创建的状态条目是否覆盖该 Fisk 场景门的脚本与碰撞状态，以及客机的 load 完成后是否实际应用到同一个场景实例。若确证未覆盖，则需要由主机把已发生的通路状态作为入场快照发送，待客机相应场景对象存在后同时应用门动画终态与碰撞终态；已连接玩家的后续开门事件也须传播。此为条件性开发方向，尚不是本包可用修复。

最少缺一组能闭合门对象语义的材料：对应 DLL 源码/符号（GameNet/GameStateSystem 注册及门状态复制入口），或同一次主机与客机的门对象/脚本及碰撞状态、GameStateRegistry 条目和快照应用日志。只有“任务目标相同”和连接成功日志仍不足以识别缺字段还是应用失败。
