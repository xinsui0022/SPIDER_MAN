# 一、第三阶段目标

本轮只提交方案，**没有启动游戏、安装工具、执行监测、创建备份或修改文件**。

第一轮只回答一个有限问题：

> 在 Client 不主动推进任务的条件下，Host 启动任务前后，Client 是否出现可重复的任务相关变化？这些变化与哪些进程的网络活动在时间上相关？

第一轮建议限定为：**建立连接 → 静止基线 → 菜单对照 → Start Mission → 观察**。一个 Objective 的推进作为追加步骤；Checkpoint、任务完成、重进和角色对调放到后续。

证据等级始终按以下标准使用：

- **Confirmed**：直接记录到的事实，例如某 PID 加载了指定路径的 DLL，或 Client 显示了某条任务文字。
- **Suspected**：重复实验支持某种联系，但尚未闭合机制，例如 Host 启动任务后 Client 总会出现相同任务。
- **Unknown**：消息内容、任务权威、持久化语义等仍没有证据。

**“两端显示相同任务”可以是 Confirmed 的观察结果；“Host Mission State 经网络复制到 Client”仍需更多证据。**

# 二、需要准备的工具

建议最小组合：**PowerShell + 双端画面记录 + Process Monitor**。需要判断数据突发时，再加 Windows 内置 Pktmon。

| 工具                             | 用途                                                         | 是否必须                                 | 是否修改游戏或进程                             | 风险与边界                                                   |
| -------------------------------- | ------------------------------------------------------------ | ---------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------ |
| Windows PowerShell，优先 64 位   | 查询 PID、EXE 路径、命令行、模块路径/基址、TCP/UDP 端点、文件哈希 | 基础检查需要                             | 所列查询不写目标进程；导出结果会新建记录文件   | 低风险；权限不足会导致查询不完整，不能把失败解释成模块不存在 |
| 任务管理器／资源监视器           | 人工确认进程和粗略网络活动                                   | 可选辅助                                 | 查看操作不修改目标                             | 无法可靠捕捉短时突发，也不能识别 Mission 消息                |
| Process Explorer                 | 直观看 DLL 列表、路径、基址和进程身份                        | 可选，可替代部分 PowerShell 查看         | 仅使用查看功能，不操作结束、暂停等按钮         | 首次运行可能保存工具设置、使用驱动；不能称为完全不改变系统   |
| Process Monitor                  | 提前记录模块加载事件；观察游戏对存档/配置的文件操作；有条件时查看事件调用栈 | 要得到本轮实际加载时间，建议使用         | 不需要向游戏注入 DLL 或打补丁                  | 会启用系统监测、可能加载驱动、写工具设置和日志；增加运行开销，须先确认 |
| Windows Pktmon                   | 记录包时间、方向、协议、地址、端口、长度，比较基线与事件窗口 | 判断突发、UDP 对端时需要一种包级记录工具 | 不需修改游戏协议或游戏内存                     | 启用系统抓包并写 ETL 文件，须先确认；记录可能含其他通信      |
| 手机拍摄两端画面，或已有录屏工具 | 保存任务文字、UI、世界变化和时间标记                         | 需要某种双端画面证据                     | 手机不触及游戏；软件录屏会启动采集并写视频     | 手机最少干预；软件录屏需确认，首轮避免新增会注入游戏的捕获组件 |
| Wireshark                        | 后续离线查看转换后的抓包                                     | 首轮不必安装                             | 离线分析不接触游戏；安装或实时捕获另有系统影响 | 先用现有工具；无需为首轮额外安装抓包驱动                     |

Process Explorer 支持查看进程已加载 DLL；Process Monitor 支持事件属性、调用栈和文件日志；Pktmon 是 Windows 内置网络诊断工具。[Process Explorer 文档](https://learn.microsoft.com/en-us/sysinternals/downloads/process-explorer)、[Process Monitor 文档](https://learn.microsoft.com/en-us/sysinternals/downloads/procmon)、[Pktmon 文档](https://learn.microsoft.com/en-us/windows-server/networking/technologies/pktmon/pktmon)

**模块加载怎么确认**

两端分别记录：

```
机器标识、实验编号、角色
游戏 PID、进程启动时间、EXE 完整路径、实际命令行
模块名称、完整路径、基址、映像大小
模块加载事件时间、采集是否覆盖进程启动
```

重点检查：

- 游戏实际安装目录内的 `winmm.dll`，并区分系统目录中的另一份 WinMM。
- 实际加载的 `SMT\Scripts\smt.dll`，核对它是否就是已审计文件。
- `steam_api64.dll`、`miniupnpc.dll` 的实际路径，不预设它们来自哪里。
- 已加载模块对应磁盘文件的哈希，避免审计目录与实际部署目录不是同一份。

**路径与基址用模块快照；准确加载时间用提前启动的 `Load Image` 事件记录。**

PowerShell 快照只能证明“查询时已加载”。文件修改时间、PE 时间戳和进程启动时间都不是 DLL 加载时间。监测如果开始晚了，应填“加载时间 Unknown”，不能补猜。

**网络连接怎么确认**

先做系统级端点快照，找到 TCP 7637、UDP 7638 的所属 PID；再检查游戏 PID 的**所有端口**，防止遗漏临时端口或其他通道。

| 对象           | 记录内容                                            | 限制                                                         |
| -------------- | --------------------------------------------------- | ------------------------------------------------------------ |
| TCP            | PID、本地/远端 IP 与端口、Listen/Established 等状态 | 连接没变化也可能一直传输数据                                 |
| UDP            | 本地绑定地址、端口、所属 PID                        | UDP 没有 TCP 式监听/已连接状态；端点表通常不能列出全部实际对端 |
| 双端抓包       | 协议、源/目标地址和端口、方向、时间、长度           | 用来补 UDP 对端和流量特征，不能直接确定发送模块              |
| 网络事件调用栈 | 如果采得到，记录模块和偏移                          | 可能只看到系统或工作线程栈，不能保证追溯到任务入口           |

PowerShell 可用 `Get-NetTCPConnection` 和 `Get-NetUDPEndpoint` 查询端点归属。[TCP 查询文档](https://learn.microsoft.com/en-us/powershell/module/nettcpip/get-nettcpconnection?view=windowsserver2025-ps)、[UDP 查询文档](https://learn.microsoft.com/en-us/powershell/module/nettcpip/get-netudpendpoint?view=windowsserver2025-ps)

特别注意：

- 7637/7638 当前首先是静态审计中的端口映射线索，实际使用情况待验证。
- TCP/UDP 承担什么业务，应从实验中调查，不能预设“TCP 是任务、UDP 是位置”。
- NAT 或中继可能让两端看到不同地址，不能强行逐项相等。
- Pktmon 可能在多个网络组件记录同一个包；统计时选定观察位置或去重，避免把重复记录当突发。

**第一轮可以可靠争取确认到进程；模块级责任归属允许继续 Unknown。**某 DLL 被加载、某 PID 有通信，两者不足以证明该 DLL 发送了任务数据。

# 三、实验前备份

**备份也会新建文件，因此此处只是清单，实际复制需要你确认。**

Host 和 Client 分别备份，不能只备份 Host：

| 备份项                     | 范围与目的                                                   |
| -------------------------- | ------------------------------------------------------------ |
| 整个 `SMT\Save\`           | 所有槽位、手动存档、`.backup*`、`SMT_SAVE_BACKUP*`、用户偏好；不要只复制当前槽位 |
| 三份配置                   | `Connections.json`、`Multiplayer.json`、`Preferences.json`   |
| 实际游戏普通存档目录       | Mod 重定向范围未完全确认，不能假定普通存档绝不受影响；路径待只读定位 |
| 整个实际部署的 `SMT` 目录  | 建议作为实验前完整副本，包含 UI、资源、脚本、配置和存档      |
| 三个核心发布文件及配套文件 | 建议保存一份原始发布包，并记录实际部署文件的哈希；现有 `cache` 也保留 |
| 游戏及 Mod 环境信息        | 游戏版本、EXE 路径与哈希、Mod 哈希、选中槽位、角色和初始任务状态 |

备份应在游戏完全退出后进行，放在游戏及 Mod 目录之外，以机器和实验编号区分。不要覆盖旧备份。

先核查 Steam Cloud 等同步是否可能接触这些目录；**不自动关闭云同步，也不自动恢复存档**。恢复是覆盖操作，需要另行确认。

最关键的限制：

> 启动游戏、加入会话、启动任务、推进目标、退出游戏，都可能触发自动存档或配置写入。只读监测工具不能阻止游戏自身写文件。

因此，正式实验前必须明确允许哪些游戏行为及其可能产生的写入。**如果要求 Save 连游戏自身都绝不能写，就不能保证安全执行任务实验。**本方案不通过改权限、拦截写入或 Hook 来规避这一点。

# 四、第一轮最小实验步骤

以下全部是未来步骤，**现在不执行**。正式执行前确认备份、日志保存位置、监测方式，以及允许的游戏操作和自动存档影响。

## Step 1：登记环境与初始条件

- **Host：**记录 Player A 的游戏/Mod 版本、部署目录、选中槽位和已有任务。
- **Client：**Player B 做相同记录，特别注明是否已有同名任务。
- **观察：**两端任务名、目标文字、位置、难度、已知进度是否不同。
- **记录：**实验编号，如 `R01_AHost_BClient`；两端文件哈希和初始条件。
- **获得证据：**后续差异是否可能源于版本或存档差异。

此步骤涉及进入游戏的部分，放在 Step 3 获准启动后补记。

## Step 2：准备统一时间线和监测

- **Host / Client：**使用同一时间格式，例如 UTC，保留毫秒字段；同时记录本机单调递增的相对时间。
- **观察：**系统时钟同步状态及两端可能的时钟偏差。
- **记录：**每条证据包含机器、角色、实验编号、绝对时间、相对时间、视频位置。
- **获得证据：**两端画面、日志和抓包可以在已知误差范围内对齐。

建议：

- 实验开始前核查时钟；不要在采集中强制校时。
- 若无法量化两端偏差，明确填“跨机时序误差 Unknown”，不要比较毫秒级先后。
- 视频中保留可对应本机日志的时钟画面或起始标记。
- 人工记录注明估计误差，例如 ±1 秒；显示了毫秒不代表具有毫秒精度。
- 不在游戏内注入时间标记，也不发送自定义游戏消息。

模块加载监测必须在游戏启动前开始；监测日志和抓包写入独立证据目录。工具启动和落盘须先获确认。

## Step 3：获准后启动两端，验证模块

- **Host：**通过原有启动流程进入游戏。
- **Client：**相同。
- **观察：**实际命令行是否含 `-mp`，四个目标 DLL 的路径和加载事件。
- **记录：**PID、进程启动时间、模块基址、完整路径、加载时间和哈希。
- **获得证据：**证明本轮实际运行了哪份游戏和 Mod。

**影响：可能写配置、缓存和存档，需提前确认。**如果模块路径或核心哈希与预期不同，先暂停实验判读，不混用第一阶段 RVA。

## Step 4：Host / Join，并记录连接阶段

- **Host：**建立会话。
- **Client：**加入，完整记录连接提示，尤其 `Syncing game state` 开始和结束。
- **观察：**监听进程、连接建立、UDP 对端、两端入场后初始世界和任务状态。
- **记录：**T0＝两端均完成入场；此前各连接阶段单独打点。
- **获得证据：**会话建立阶段与任务启动阶段的通信可以分开比较。

不要用 Host 菜单出现“已连接”替代 Client 已完成创建世界的证据。建会话也可能产生配置写入或 UPnP 映射，纳入事前确认。

## Step 5：采集静止基线与菜单对照

- **Host：**静止约 30 秒；随后打开任务菜单但不启动，关闭后再等待约 15 秒。
- **Client：**保持静止，不接任务、不进触发区；记录远程玩家是否仍正常。
- **观察：**正常包频率、方向、长度分布、背景敌人或随机事件。
- **记录：**静止和“只开菜单”两个独立时间窗口。
- **获得证据：**区分持续实体同步、菜单行为和实际任务启动。

尽量选择安全、可观察的地点；不要为清理环境临时修改犯罪开关或其他配置。

## Step 6：Mission Start 核心实验

选择两端已记录初始条件的、短且可观察的任务，优先简单到点目标。**现在不指定任务名称：尚不知道这份存档实际可用哪些任务。**

- **Host：**只点击一次 Start Mission，随后尽量不移动、不战斗。
- **Client：**不启动任务、不推进本地任务、不主动进入触发区。
- **观察：**任务名、Objective 文字、标记、过场、敌人/NPC、时间天气、世界变化。
- **记录：**T1 点击；T2 Host 首次出现任务；T3 Client 首次变化或观察窗口结束。
- **获得证据：**Host 启动与 Client 变化的时间关联。

建议保留 T1 前 15 秒、后至少 60 秒记录；有加载过程则延长并注明。分别看点击、Host 实际进入任务、Client 首次变化三个窗口。

同时记录有无新连接、既有连接是否出现数据突发。**新连接不是同步的必要条件；网络流量变化也不等于已证明 Mission 同步。**

**这一动作可能自动存档，必须明确确认后执行。**

## Step 7：可选追加一个 Objective

仅在任务正常、没有异常写入或状态问题，且已明确允许推进后执行。

- **Host：**完成一个明确动作，例如到达指定位置，使目标 A → B。
- **Client：**不主动完成该条件；如果过场或传送强制移动，记录为被动变化。
- **观察：**两端目标文字、世界实体、任务标记及 Remote Player 行为。
- **记录：**T4 Host A → B；T5 Client 变化时间、内容，或“窗口内未观察到”。
- **获得证据：**变化是否超出任务启动，延伸到目标推进。

首轮不要同时测试多个目标。Client 单独尝试完成条件属于另一实验，需要重新确认。

## Step 8：结束本轮观察

- **Host / Client：**记录当前状态，停止新增实验动作。
- **观察：**监测中是否出现对 Save、配置或缓存的成功写入。
- **记录：**保存视频、原始日志、抓包、模块快照和事件表。
- **获得证据：**形成可复核的一次运行记录。

**退出游戏也可能保存状态，应包含在先前批准的操作范围内，否则先等待确认。**正常退出后再比较存档哈希；不自动恢复。

文件被打开不等于被写入；成功写入或哈希改变也不等于“剧情进度同步”，还需分析改变内容。

## 后续保留实验：本轮不做

| 实验                 | 操作设计                                                     | 判断边界与风险                                               |
| -------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| Checkpoint           | 先被动记录 Host 到达 T6 时两端变化；另轮分别测试 Host 重载、Client 重载，避免同时操作 | 到检查点就可能自动保存；死亡、重载和恢复均可能改变进度，需单独确认 |
| Mission Complete     | 记录 T7 两端完成提示、下一任务、奖励和世界变化；退出后比较各自存档 | 任务完成很可能写 Save；文件变化不能独立证明 Story Progression |
| 退出重进             | 先完成双端备份；分别观察 Client 独立加载、再加入 Host 后的状态 | 区分本地持久化和入场覆盖；退出、重进、单独加载都需确认       |
| 角色对调             | `A Host / B Client` 后再做 `B Host / A Client`，使用相同任务和操作序列 | 一次对调会同时改变主机和主机存档，存在混杂；需要控制各机器自己的初始存档 |
| 带活动任务的加入对照 | 比较 Host 无活动任务和已有活动任务时，Client 的入场结果      | 最有助于研究 `Syncing game state`，但需控制 Client 初始条件，另轮批准 |

Checkpoint 不能仅凭“回到相同位置”判定一致，还要比较任务、目标、敌人重置和阶段。Client 能否独立重载到同一阶段，才有助于判断对本地 Save 的依赖。

| 标记及目的地      |              |                         | 指引是否变化                 |
| 敌人/NPC/世界物件 |              |                         | 可见世界是否变化             |
| Remote Player     |              |                         | 远程玩家行为是否正常         |
| Client 自身操作   | 不适用       | 静止/移动/战斗/被动传送 | 是否存在本地触发条件         |
| Save 操作         |              |                         | 是否发生写入，不直接解释进度 |

“Client 完全没有任务状态”不是可靠的画面观察项。应填写：**“未显示任务、未观察到任务相关世界变化；内部状态 Unknown。”**

# 六、不同结果的解释

## A. Host 开任务后 Client 同时出现任务

- **Confirmed：**两端显示了对应任务及各自出现时间。
- **Suspected：**存在任务启动事件、任务快照或其他共享状态传播。
- **Unknown：**是否复制了 Mission State，是否支持后续目标和完成。

下一步优先测试 **Client 静止时的 Objective A → B**，并检查 Client 是否原本已有该任务、是否被共同传送触发了本地逻辑。随后调查 T1 到 T3 之间的收发、状态应用与 UI 更新边界。

## B. Host 开任务后 Client 不出现任务，但出现网络流量

- **Confirmed：**有通信，观察窗口内 Client 未显示任务。
- **Unknown：**通信是否包含任务数据。

优先区分流量来自玩家位置、传送、敌人、加载，还是任务相关事件。若 Client 世界也变化，进一步看世界复制与任务 UI 的边界；如果两者都不变，再调查接收分发、消息忽略条件及版本差异。

不能直接判为“任务包发出了，但 Client 没处理”。

## C. Host 开任务后 Client 不出现任务，也没有明显新流量

- **Confirmed：**在当前采集范围和精度下没有识别到明显变化。
- **Suspected：**任务启动可能只影响本地。
- **Unknown：**是否有很小的消息、周期包内字段变化、其他通道、延迟发送或采集遗漏。

先核查抓包覆盖、既有连接、其他端口和丢事件情况。重复结果稳定后，优先逆向 `SMT_StartMission` 后的调用链，寻找是否触发网络脏标记、事件队列或状态发布。

**“无明显突发”不能升级为“没有发包”。**

## D. Client 世界变化，但 Objective UI 不出现

- **Confirmed：**可见世界改变，目标 UI 未出现。
- **Suspected：**世界/实体复制与任务目标呈现可能分离。
- **Unknown：**Client 是否有内部任务状态、仅收到世界事件，或被位置变化触发了本地事件。

优先比较 NPC、敌人、区域触发与 HUD 更新；之后追踪接收事件到任务系统/UI 的连接。不要立即将问题归为 UI Bug。

## E. Client 自己有任务，但与 Host 进度不同

- **Confirmed：**两端可见任务或目标不同。
- **Suspected：**可能各自运行本地任务逻辑，或者只同步启动、不同步推进。
- **Unknown：**Host 权威规则、Client 是否被设计为旁观远程角色、Save 如何参与。

优先核查两端初始存档和 Client 自身触发条件，再做受控角色对调。只有 Remote Player 表现正常，不能证明 Client “只有远程玩家功能”。

**最有价值的逆向观察点**

| 对象                 | 值得捕捉的现象                     | 如何缩小范围                                                 |
| -------------------- | ---------------------------------- | ------------------------------------------------------------ |
| `SMT_StartMission`   | 点击后 Host 首次进入任务的时间窗口 | 对齐已知注册/回调 RVA `0x61890`、`0x61910` 和包装函数 `0x2D920` |
| `Syncing game state` | 加入时任务、世界、玩家分别何时出现 | 区分入场快照与运行中事件传播                                 |
| Save                 | 哪个进程何时读取或成功写入哪个路径 | 区分本地加载、运行状态和落盘；不把写入直接当剧情同步         |
| Remote Player        | 任务不一致时移动/动作是否仍正常    | 判断连接整体正常但某类状态未一致                             |
| Host / Join          | 角色、连接阶段和状态差异           | 缩小会话初始化、权限与入场分支                               |
| 网络连接             | 可重复的方向、长度和时序变化       | 选择值得继续分析的收发窗口                                   |
| Mission UI           | 任务名、目标文字、标记分别何时改变 | 分开调查任务状态与界面呈现                                   |

没有符号时，**“同一触发在对照实验中反复产生同一差异，并有准确时间窗口”**最有价值。如果监测工具恰好提供有效调用栈，可记录 `模块名 + RVA`；没有拿到栈就继续保留 Unknown。

上述已知 RVA 只适用于哈希一致的核心 DLL。本轮不通过断点或 Hook 去验证它们。

# 七、禁止现在做的事情

- 不启动游戏、建立 Host/Join、点击 Start Mission 或推进目标。
- 不安装或启动监测工具，不开始抓包、录屏或生成日志文件。
- 不创建、覆盖或恢复备份；不改 Save、配置、缓存或云同步设置。
- 不 Patch Launcher、WinMM、核心 DLL、游戏 EXE 或游戏 DLL。
- 不注入 DLL、不新增 Hook、不调用内部任务函数、不写游戏内存。
- 不使用软件断点；硬件断点、暂停线程、调试器附加等也不纳入首轮。
- 不重放、伪造、拦截或修改游戏网络消息。
- 不生成替代 DLL、不实现同步、不重构。
- 不执行死亡、重载、完成任务、退出重进或角色对调实验。
- 不依据单个字符串、流量突发或 UI 变化宣布 Mission 同步已实现或不存在。

**建议批准执行时的最小范围是 Step 1—6：完成备份和监测准备后，只做一次任务启动观察。Objective 及之后的实验根据结果另行决定。**
